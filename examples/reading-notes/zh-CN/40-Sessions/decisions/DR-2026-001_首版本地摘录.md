# 首版先支持本地摘录和检索，暂缓多人共享

<!-- Loom 文档的演示数据，不是真实项目。 -->

## 1. 要决定的问题
只有一个人、没有服务器预算，[[方案备选]] 中的三个方案，首版采用哪一个？

## 2. 背景与约束
- 现状：需求见 [[需求笔记]]；三个候选方案的对比见 [[方案备选]]。
- 时间窗口：首版应该在几个周末内可用。
- 硬约束：不要服务器、不要账号、文件必须是纯文本。
- 与项目目标的关系：简报里的核心价值是事后找到摘录，不是分享。

## 3. 选项
| 选项 | 核心收益 | 核心代价 | 最坏情况 | 可逆性 |
|---|---|---|---|---|
| A. Markdown + 本地检索 | 零基础设施，文件归我 | 结构化查询弱 | 规模上去后检索变难用 | 可逆 |
| B. SQLite + 命令行 | 结构化、过滤查询快 | schema + 导入摩擦 | 工具本身变成负担 | 可逆 |
| C. Web 应用 | 同步和共享 | 服务器、账号、维护 | 项目被自身重量压垮 | 基本不可逆 |

## 4. 分析
- 只有 C 带共享，而 C 违反全部硬约束。A 和 B 之间，A 最贴合"文件归我"，且以后可以演化成 B。

## 5. 最强反方论证
- 摘录攒到几百条后，纯文本检索可能确实太弱，而在松散的笔记上补结构很痛苦。

## 6. 事前验尸（假设一段时间后发现这个决定失败了，最可能的原因是什么）
- 摘录量增长很快，临时检索不再够用，而把一堆自由格式笔记迁进 SQLite 比一开始就做 B 还费事。

## 7. 决定
- **选择**：方案 A——首版支持本地摘录和检索，暂缓多人共享。
- **理由**（不超过 3 条）：零基础设施；文件归我；A 可以不丢数据地演化成 B。
- **信心度**：70%
- **放弃了什么**：首版的多设备同步和共享。

- 应当重新考虑的信号：经常找不到摘录，或真的出现了第二个用户。
